先读包内[共同执行边界](../../references/workflow.md)，定位用户指定的项目。没有本地文件或 shell 时说明缺少的能力，只提供接入计划；插件安装不代表模板已接入。

区分三种情况：

- **空目录**：确认目标存在，按共同边界取得并核实官方模板源。在源主目录预演 `pnpm agent -- template update "<目标>" --scope agent --initialize --dry-run`；无冲突时去掉 `--dry-run` 安装，再复查。首次初始化后完整读取目标三份基础规则。源与目标都不为文件安装创建 worktree。
- **已有 Git 项目，尚未接入**：先读已有项目规则；同样使用 `--initialize`，直接安装到指定主目录，有无提交均可，不执行目标 Git 生命周期。保留 `.git`、暂存区和业务文件，文件冲突先处理，不强行覆盖。
- **已接入息壤**：在对应实际项目完整读取基础规则，登记或恢复更新任务，在干净的专用 worktree 内执行 `pnpm agent -- template sync`，继续该项目规定的交付链；固定官方 GitHub main，不传替换来源参数。旧版缺基线或入口不支持参数时先诊断，不自行采用当前 HEAD 充当旧基线。

默认只接入作业包。用户需要架构选型时再单独追加 architecture；接入请求本身不授权迁移技术栈、部署或自动联系协作者。

成功报告必须区分：模板安装与收敛、项目环境配置、业务验证、远端交付。只证实前一项时不要宣称后面全部完成。列出真实目标路径、来源提交和未满足的下一项。
