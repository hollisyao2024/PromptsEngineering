先读包内[共同执行边界](../../references/workflow.md)，定位用户指定的项目。没有本地文件或 shell 时说明缺少的能力，只提供接入计划；插件安装不代表模板已接入。

区分三种情况：

- **空目录**：确认目标存在，按共同边界取得并核实官方模板源。在源中预演 `pnpm agent -- template update "<目标>" --scope agent --dry-run`。向用户简述文件变更与冲突；已有接入授权且无冲突时继续应用。首次初始化后完整读取目标的三份基础规则，再执行其他项目副作用。再次预演须收敛。
- **已有 Git 项目，尚未接入**：先读已有项目规则，按该项目的生命周期建立干净专用 linked worktree；把它作为 update 目标。不覆盖主工作区或绕过已有规则来创建它。存在实际选择歧义时只问必要信息。
- **已接入息壤**：完整读取基础规则，登记或恢复更新任务，在干净的专用 worktree 内执行 `pnpm agent -- template sync --scope agent`，继续该项目规定的交付链。旧版缺基线或入口不支持参数时先诊断，不自行采用当前 HEAD 充当旧基线。

默认只接入作业包。用户需要架构选型时再单独追加 architecture；接入请求本身不授权迁移技术栈、部署或自动联系协作者。

成功报告必须区分：模板安装与收敛、项目环境配置、业务验证、远端交付。只证实前一项时不要宣称后面全部完成。列出真实目标路径、来源提交和未满足的下一项。
