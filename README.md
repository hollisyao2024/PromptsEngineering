# 息壤（Xirang）

**让不同大模型、不同开发者，在同一个项目中有序协作。**

息壤是一套面向 AI 辅助开发的工程协作模板：用统一项目规则连接不同模型，用独立 Git worktree 隔离并行任务，用测试与 QA 门禁把修改交付到主干。

**多模型接力 · 多人多机协作 · 单机多任务并行 · 中断可恢复 · 交付可验证**

[常用指令](docs/guides/commands.md) · [快速上手](docs/guides/quickstart.md) · [插件入口](docs/guides/plugin-quickstart.md) · [并行协作教程](docs/guides/parallel-collaboration.md) · [完整使用参考](docs/guides/template-reference.md) · [English](README.en.md)

## 一个项目，三种协作方式

| 协作场景 | 怎样使用息壤 |
| --- | --- |
| **多模型开发同一项目** | Claude Code、Codex、Gemini CLI 等工具遵循同一套项目规则、验收与交付流程；切换工具时，依据任务状态、证据和上下文胶囊继续工作 |
| **多人、多电脑并行开发** | 每项任务使用独立分支和 worktree，各自开发、验证、提交 PR；合并前复验主干与待合并提交，避免用过期验证覆盖他人交付 |
| **一台电脑并行多个任务** | 同时打开多个 AI 会话，每个会话进入自己的 worktree，分别安装依赖、修改和测试，减少工作目录相互覆盖与依赖目录相互干扰 |

这三种方式可以组合：团队成员使用不同 AI 工具，每个人也可以在自己的电脑上并行推进多个独立任务。

worktree 隔离文件与依赖目录；共享服务、端口、数据库和业务接口仍需项目协调。并行开发不等于零冲突：同一接口、同一文件或相互依赖的需求，要先约定边界，再处理合并与验证。

## 从开工到交付，统一一套流程

- **规则统一**：项目约定写进仓库，不随聊天窗口或模型切换而重新定义。
- **任务独立**：每项修改有任务 ID、明确验收和专属工作区，减少相互覆盖。
- **中断可续**：任务状态、执行证据与上下文胶囊记录进展，换会话时有据可查；跨电脑合并需重新执行本机 QA。
- **交付可查**：修改经过定向验证、PR 和 QA；合并前再次核对提交 SHA，漂移或冲突时停止，重新同步验证。
- **更新有边界**：模板与项目文件分清所有权，通过版本基线和三方更新保留定制、显式报告冲突。

日常修复、重构和文档维护走轻量流程；需求、架构或外部合约变化时，按 PRD → ARCH → TASK → TDD → QA 推进，涉及环境与发布再进入 OPS。规则、命令和证据共同约束执行，完成标准不只是一句“代码写好了”。

## 适合谁

- 希望按任务选择不同 AI 工具，又保持项目规则和交付标准一致的开发者。
- 希望一台电脑打开多个 AI 会话，同时推进独立任务的个人开发者。
- 需要多人、多电脑并行开发，共享验收与合并约定的团队。
- 已有代码库，希望先接入协作流程，再按需采用架构模块的维护者。

如果只是一次性脚本或没有协作需求的小实验，先评估任务与 QA 流程的成本。息壤需要 Git、Node.js、pnpm，以及团队实际执行约定；它不是一键开启的自动调度服务。

## 先跑通一次接入

先采用**模型作业包**。它提供协议、任务、worktree 和交付工具，不要求更换现有技术栈。

在息壤源项目的 AI 会话中说“初始化项目，路径为 `<目标绝对路径>`”，即可自动检查、预演、安装文件和复查，不操作目标 Git。默认只接入作业包；已有 Git 仓库同样可初始化，直接在源与目标主目录操作，无需为安装创建 worktree。更新时打开对应实际项目，说“更新息壤模板”，固定从 GitHub 官方源的 `main` 获取最新版。详见[常用指令](docs/guides/commands.md)。

在已获取的息壤源仓库执行，目标目录须存在；初始化模式支持已有 Git 仓库，保留 Git 元数据：

```bash
pnpm agent -- template update "<目标目录>" --scope agent --initialize --dry-run
pnpm agent -- template update "<目标目录>" --scope agent --initialize
```

从获取源码、准备环境到检查生成结果，按[快速上手](docs/guides/quickstart.md)操作。首次接入成功的判据是：生成协议和基线文件，再次预演无待应用差异；业务测试通过是后续项目验收。

## 怎样开始并行开发

1. 约定任务边界、共享接口和各自验收。
2. 每人或每个 AI 会话登记独立任务，创建自己的 worktree。
3. 在各自 worktree 完成修改与定向验证，生成 PR。
4. 对固定提交执行 QA；主干变化或提交漂移时重新同步、验证。
5. 合并后核对主干与远端，再按生命周期门禁清理。

[双任务协作教程](docs/guides/parallel-collaboration.md)提供可复制的任务指令、关键命令和冲突处理方式。

例如：一个会话开发独立模块，另一个会话补充另一模块的测试或文档。先拆清文件和接口归属，再分配给不同模型或团队成员；共享接口与依赖锁文件的修改要约定负责人和合并顺序。

本机锁只协调当前电脑的生命周期操作；跨电脑交付通过远端 SHA 复验与普通 push 的非快进拒绝保护主干。主干发生变化时，按门禁提示重新同步与验证。

## 与 AI 编程工具配合

息壤以仓库文件和 CLI 命令作为协作接口，不绑定单一模型。仓库已提供以下工具入口：

| 仓库提供的入口 | 用途 |
| --- | --- |
| `AGENTS.md` | 通用规则、阶段路由与交付约定 |
| `CLAUDE.md`、`.claude/` | Claude Code 的规则入口与配置材料 |
| `.codex/` | Codex 的配置材料；通用规则从 `AGENTS.md` 进入 |
| `GEMINI.md`、`.gemini/` | Gemini CLI 的规则入口与配置材料 |

其他 AI 编程工具也可按相同协议接入，前提是能读取项目规则、操作文件并执行所需命令。实际兼容性取决于客户端能力与权限，已有入口也不代表所有版本组合均已验证。接入前按[工具接入检查](docs/guides/quickstart.md#工具接入检查)确认规则确实被加载、命令可以运行。

已有 `0.1.0` 轻量插件，提供接入、启动任务、恢复、检查交付四项技能；Claude Code 与 OpenAI 本地市场清单指向同一份源码。安装步骤与实际验证范围见[插件上手](docs/guides/plugin-quickstart.md)。尚未提交公共市场，插件安装也不代表目标项目已接入模板。

## 按需采用架构能力

协作流程与应用架构可以独立采用。需要架构规划入口时追加 `--include architecture`，再按项目选择运行 `architecture plan/init/check`。不要与 `--scope agent` 同时使用。

架构包包含多端 Monorepo 蓝图、UI 组件、存储与开源模块的选型和生成材料。实际可用项、采用条件与边界以[架构包说明](architecture/README.md)及[组件目录](architecture/open-source-catalog.json)为准；它不是所有技术栈的通用生成器。
