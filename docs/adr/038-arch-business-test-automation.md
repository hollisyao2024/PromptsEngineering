# ADR-038：业务测试采用“创作期推导、脚本期确定性判定”

- 日期：2026-10-06
- 状态：Accepted
- 关联：US-BIZTEST-001、US-BIZTEST-002、US-BIZTEST-003、US-BIZTEST-004、US-BIZTEST-005、US-BIZTEST-006
- 后续补充：2026-10-08 依据真实项目试验修正 `qa run` 的退出语义、回执的可选业务摘要、`task exec` 对已登记套件命令的放行，以及 QA 生成器与 `qa verify` 对 PRD 表格的识别，见文末「后续补充（2026-10-08）」；决策第 6 条的「回执结构不变」与取舍中的「本期不扩展回执结构」由该节更正，其余决策不变。

## 背景

实际项目需要依据 PRD 对页面与客户端做业务测试。既有 QA 指引只写明“可以生成用例”，没有规定生成依据、路径如何收敛、结果如何证明，`qa verify` 也无法判断 P0 验收是否真被测过。页面操作路径随状态与取值组合爆炸；模型生成的用例还可能只是复述被测代码的当前输出，使测试变成循环验证。

## 决策

1. **分层**：模型只在创作期工作，产出可评审的文件（原子 AC、路径模型、数据驱动用例）；运行、绑定与判定由脚本确定性完成，不调用模型、不联网、不引入随机。
2. **规格契约**：模块 PRD 用 9 列原子 AC 表（`AC ID | Story | 优先级 | 验证 | 端 | Given | When | Then | TC`），一条 AC 只断言一个可观察结果；测试用例标识统一为 `TC-{MODULE}-NNN`。
3. **路径模型**：`docs/qa-modules/<domain>/PATHS.md` 以界面、状态、转移、路径四张表加覆盖准则（`all-states`、`all-transitions`、`none`）把业务操作建模为状态机；脚本校验引用、衔接与覆盖，以覆盖准则而非穷举收敛路径数量。
4. **驱动无关接口**：只约定 JUnit XML 报告、用例名携带 AC/TC 标识、套件 `platform` 标签；Playwright、Maestro、XCUITest、Espresso 等由项目选择。
5. **结果证据**：`qa run` 在容器 `tmp` 写 `ac-results.json`，绑定 HEAD SHA、运行前工作区洁净状态、配置摘要与报告副本 SHA256；`qa verify` 重新解析报告副本与当前规格，并与记录逐项比对。
6. **门禁**：`qa.business.enabled` 默认 `false`；开启后在 `qa verify` 的测试范围证据校验之后、回执写入之前判定；模板源跳过，回执结构不变。

## 取舍与后果

- 拒绝“门禁时调用模型判定”：结果不可复现、有成本、易受被测内容注入影响；模型的价值在创作期，产物经评审后固化为文件。
- 拒绝穷举 UI 路径：用例数随路径与取值组合爆炸；覆盖准则选路径，等价类、边界值、判定表、两两组合只生成数据行，变体下沉到 API 层，UI 保留关键旅程。
- 拒绝内置某一驱动或脚手架：会把模板绑定到技术栈；JUnit 约定对 Web 与四类客户端通用，驱动脚手架留给 architecture 包后续提供。
- 拒绝把结果提交进仓库或写入任务状态：前者引入噪声且易手改，后者与任务生命周期耦合，夹具难以独立验证；结果放容器 `tmp`，生命周期与 QA 回执一致。
- 拒绝因套件退出码非零一律阻断：Playwright 等驱动在任一用例失败时整体退出非零，会使“低于必需优先级的失败只披露”无法成立；改为由 AC 绑定判定，并把无法启动、超时、缺少或无法解析报告视为硬失败。
- 本期不扩展回执结构：回执继续只绑定配置主干与功能分支 SHA；把业务结果摘要写入回执留作后续审计增强。
- 信任边界与既有本地门禁一致：结果防篡改仅指“被改动可被发现”，不防同时伪造报告副本与记录；模板不宣称服务端零信任。
- 代价：既有 PRD 不改表格就不受门禁约束，因此门禁把“无原子 AC 表的模块”作为风险披露，避免静默失效；P0 用例与路径仍需人工评审，预言机污染只能靠指引、评审与夹具反例降低，不能被脚本证明为零。

## 后续补充（2026-10-08）

起因：2026-10-08 在一个真实下游项目里从零接入业务测试，跑通 `qa paths`、`qa run`、`qa verify` 全链路（试验项目已清理）。试验暴露了本 ADR 落地中的三处缺口，在 v3.11.0 修正；本节记录这些修正与取舍，决策的分层、规格契约、路径模型、驱动无关接口与结果证据五项不变。

`qa run` 的退出语义。原实现只要各套件正常完成就输出 `STATUS=OK` 并以 0 退出，即使必需优先级的自动化 AC 没有通过的用例，或用例被跳过。输出会让人以为可以进入 `qa verify`，直到门禁阻断才发现。现在套件失败仍是 `STATUS=FAILED`、`REASON=SUITE_FAILED` 且优先；套件都正常完成、但 `qa.business.requiredPriorities` 内的 `auto` AC 仍未被通过的用例证明时，是 `STATUS=FAILED`、`REASON=AC_NOT_PROVEN`，并逐条输出 `AC_OPEN=<AC>|<优先级>|<状态>|<原因>`，判定与 `qa verify` 的门禁共用同一函数。这两种 FAILED 都已写出结果文件，`qa verify` 复核的仍是同一份记录；运行前就被拒绝的情形仍是 `BLOCKED` 且不写结果。`qa run` 只看已登记的套件，与 `qa.business.enabled` 无关，所以登记了套件但没有开启门禁的项目，在必需优先级 AC 未被证明时同样得到非零退出；下游若把 `qa run` 的退出码只当作“套件跑完了”，需要相应调整。门禁的判定规则本身没有变。

回执的可选业务摘要。第 6 条写“回执结构不变”，取舍里把业务结果摘要写入回执留作后续增强。现在业务门禁开启且通过时，回执可携带 `business` 摘要（`gate`、`required_priorities`、`acs_proven`、`risk_count`、`config_digest`），供事后审计。`schema_version` 仍是 1，该字段是可选的加法：没有它的回执照常有效；`qa merge` 的复验只比较 `schema_version`、`verdict`、配置主干与功能分支名、两端 SHA 和 PR 引用，不读取 `business`，旧版脚本读取带摘要的回执也只会忽略它。因此回执只绑定配置主干与功能分支 SHA 的信任边界不变，摘要是审计信息，不是合并依据；门禁未开启或模板源跳过门禁时，回执与之前逐字段相同。

`task exec` 对已登记套件命令的放行。聚合测试命令的拦截不区分来源：项目把 `pnpm test` 之类写进 `qa.business.suites` 后，`qa run` 能运行它，同一条命令交给 `task exec` 却被拦，必须为它另记一份 `mode=full` 决策。现在与某个已登记套件命令逐词完全相同的命令，在原样输入时放行。条件收得很窄：只做逐词精确匹配，不做前缀或子串匹配；已登记命令里只要有一个词含引号、变量、管道、重定向、通配符等需要 shell 解释的字符（词须匹配 `[\w@+,./:=-]+`），这一条就不参与匹配；`sh -c` 之类的包装、追加或删减参数的变体、业务配置本身无效时，都照旧拦截。这个例外不改变“无依据不跑全量”的规则：`qa run` 本就无护栏地运行登记命令，`task exec` 只是不再对同一条命令更严；其他聚合或无目标的测试命令仍须按 `docs/CONVENTIONS.md` §8 记录 `mode=full` 的触发依据。

QA 生成器与 `qa verify` 对 PRD 表格的识别。`qa:generate` 原先只认 Story 标题与行内提及，不认 9 列原子 AC 表：Story 数被行内提及虚增，用例标识按“预估”虚构并带错误前缀，`qa verify` 的 `prd-story-coverage` 因而在试验里停在 50%。现在 `business-spec.js` 导出 `parsePrdStories`，一次给出 Story 清单、Story 是否由表格定义、模块标识与 AC 行，`qa:generate` 与 `qa verify` 共用它。模块 QA 文档里的用例行按 AC 表的 TC 列归并，尚未登记用例的 AC 与没有 AC 的 Story 单列在 `### 3.2 尚未登记用例的验收标准`，不再虚构标识。没有 Story 表或 AC 表的 PRD 仍走旧的骨架路径，但 Story 提及会去重，也能识别多段、含数字的模块标识（旧模式 `/US-([A-Z0-9]+)-(\d+)/` 匹配不了 `US-MODEL-CONFIG-001`）；这是对旧行为的有意修正。已知局限：首列列出非本模块 Story 的表格（例如上游依赖表）会被算作本模块的 Story；只在标题或列表里定义 Story 的 PRD 退回提及计数；`### 3.2` 里出现的未覆盖 Story 标识仍会被 `prd-story-coverage` 当作“被引用”，该检查本来只用于展示，不参与门禁。v3.11.25 起这三项已消除：登记只保留与模块标识一致的 Story，以 Story ID 开头的标题也算登记，`prd-story-coverage` 计算覆盖前去掉 `3.2` 小节。

未变更。路径覆盖缺口（`PATH_COVERAGE_GAP`）仍只在 `qa verify` 阶段判定，`qa run` 不预告。试验还发现其他缺陷，本次没有处理，也不在本节范围。
