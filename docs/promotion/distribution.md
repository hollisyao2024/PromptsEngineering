# 插件与分发渠道评估

[推广方案](README.md) · [项目首页](../../README.md)

核对日期：2026-10-19。产品入口和审核要求可能调整，提交前重新核对下方官方文档。本页是适配方案，不是已上架声明。

## 建议路线

GitHub 主源 → 可安装的轻量插件适配 → Claude Code 自建市场试用 → ChatGPT/Codex 公共目录与 Claude 官方收录申请。

理由：息壤的核心是本地仓库、Git worktree 和交付脚本；先让已有本地开发能力的用户跑通，比先建设远程服务更贴近当前实现。公共市场有分发价值，但不能替代产品试用或保证访问量。

## 不同载体的作用

| 载体 | 适配程度 | 需要补齐 |
| --- | --- | --- |
| GitHub 仓库 | 当前主渠道 | 新手路径、真实案例、授权正文、反馈入口；保留固定上游地址 |
| Claude Code 自建插件市场 | 适合作为首个插件试验渠道 | 插件清单、聚焦技能、独立打包、本地安装与卸载验证 |
| Claude 官方插件市场 | 适合在试用稳定后申请 | 可用插件、真实说明与演示；按官方提交入口要求准备，不承诺收录 |
| ChatGPT/Codex 插件目录 | 有正式路径，需封装后评估提交 | 有效插件包、身份验证、技能扫描、元数据与客户端验证；本地执行能力须明确 |
| MCP 服务 | 未来有远端状态查询或受控操作需求时考虑 | 服务部署、认证、权限、运行状态与工具契约；当前不为上架而强加服务 |

GitHub 用于源码与长文档，插件用于进入工作流。两者可以共用一个能力来源，避免复制出互不兼容的协议版本。

## Claude Code 的具体路径

官方支持把 `.claude-plugin/marketplace.json` 放在 Git 托管仓库中，用户注册市场后安装插件。清单和技能尚未实现前，不提供假装可用的息壤安装命令。[创建市场](https://code.claude.com/docs/en/plugin-marketplaces)

Claude 官方市场提供 “Submit a plugin” 入口。自建市场可安装与官方收录是两个结果，不能相互替代。[Claude 官方插件市场](https://claude.com/marketplace/plugins)

适配包应自包含：技能引用的文件必须随包提供，不能假设安装缓存旁边存在源仓库。源模板的项目初始化与生命周期规则保留在真实项目中执行；插件不应仅靠装入全局指令就绕过 worktree 和状态门禁。

## ChatGPT / Codex 的具体路径

OpenAI 官方文档说明 ChatGPT 和 Codex 共享公共插件目录；插件可包含技能、MCP 或两者。先评估技能型适配，不因打包本身新增 MCP。[插件架构](https://developers.openai.com/plugins/concepts/plugins)

官方提交路径需要有效 ZIP、经过验证的发布者身份、自动检查和审核；批准后由发布者选择发布。公开提交当前不接收依赖 lifecycle hooks 的包，若工作流必须依赖 hook，应走手动桌面分发。工作区内发布与公共目录发布也需区分。[打包指南](https://developers.openai.com/plugins/build/plugins)、[提交指南](https://developers.openai.com/plugins/deploy/submission)

官方还提供 Claude Code 插件的转换提交路径：保留合格的技能，将可复用 commands/agents 行为转为技能，并验证引用资源与执行环境；不要把整套模板目录直接压缩后声称兼容。[Claude 插件转换指南](https://developers.openai.com/plugins/guides/submit-claude-plugin)

公共目录支持打包不等于所有客户端都能运行本地 Git/pnpm。首版应明确：完整执行需要可访问项目文件和 shell 的运行环境；缺能力时只能只读说明并报告缺口，不伪称创建了任务或完成了 QA。技能型插件的具体可发布资格以提交时官方要求为准。

## 首版插件建议能力

以下是待实现的四个用户目标，不是现有斜杠命令：

1. **接入项目**：读取规则、判断新项目/已有项目/已接入项目，预演变更，再按所有权应用。
2. **启动隔离任务**：将用户目标整理为显式验收，登记任务、创建 worktree 并切换到真实路径。
3. **恢复任务**：已知任务 ID 时恢复并刷新上下文；结果未知的副作用先核实。
4. **检查交付**：核对验证证据、固定提交和完成门禁，指出尚未通过的步骤。

实现时复用项目现有 CLI，不另造任务状态或锁。插件指令只负责发现入口与编排已授权流程；版本与能力检测失败时给出升级建议，不静默使用不兼容的旧脚本。不要自动安装全局配置、降低权限或把项目 token 放进插件。

## 适配验收与发布前置条件

- 在干净客户端安装、触发四项技能、检查反例和卸载；记录客户端版本与执行环境。
- 新项目、既有项目、无 shell、无网络、缺少凭据、中断与未知副作用均有可解释结果。
- 引用资源随包提供，运行命令来自固定来源或目标项目，校验更新与所有权边界。
- 需要 hook 的功能不混进声称可公开提交的无 hook 包；云端与桌面能力分别标注。
- 补齐发布者身份、图标、描述、支持入口、许可正文及适用的审核材料；不得虚构批准、评分或用户数据。
- 市场提交与公开发布分别取得维护者授权；保留提交状态与结果证据。

这是一个后续实现任务，不能在纯文档变更中未经测试就加入市场清单或声明兼容。先完成当前接入路径验证，再以独立验收开展插件适配。
